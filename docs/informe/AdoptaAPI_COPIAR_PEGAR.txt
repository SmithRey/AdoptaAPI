1. RESUMEN EJECUTIVO
================================================================================

AdoptaAPI es una plataforma tecnológica orientada a centralizar y digitalizar el
proceso de adopción de mascotas en Colombia. Conecta fundaciones de rescate animal
con adoptantes potenciales mediante una API REST documentada y una interfaz web MVC,
reemplazando la gestión fragmentada actual en redes sociales.

Aspecto          | Descripción
-----------------|-------------------------------------------------------------
Problema         | Información dispersa, falta de trazabilidad, procesos informales
Solución         | API centralizada con filtros, estados trazables y reportes
Usuarios         | Fundaciones, adoptantes y visitantes
Entregables      | API REST, Swagger, modelo relacional, UML, Figma, Azure
Duración         | 6 semanas (3 sprints + setup)

================================================================================
2. CONTEXTO Y OBJETIVOS
================================================================================

2.1 OBJETIVO GENERAL
--------------------
Desarrollar una API REST que centralice y digitalice el proceso de publicación,
búsqueda y seguimiento de adopciones de mascotas, conectando de forma ágil y
trazable a fundaciones de rescate animal con potenciales adoptantes.

2.2 OBJETIVOS ESPECÍFICOS
-------------------------
OE-01 | API REST documentada con Swagger → OpenAPI 3.0 en /swagger
OE-02 | Filtrado por especie, edad, tamaño y ciudad → GET /api/mascotas
OE-03 | Flujo de solicitud con 5 estados trazables
OE-04 | Reportes para fundaciones → disponibles vs. adoptadas
OE-05 | Swagger UI + mockups Figma navegables

2.3 DESCRIPCIÓN DEL PROBLEMA
----------------------------
• 58% de hogares colombianos tienen mascotas; red de rescate informal y atomizada
• Información dispersa en Instagram, Facebook, hashtags (#AdoptaEnBogota)
• Falta de confianza: adoptantes verifican manualmente rescatistas
• Proceso intrazable por mensajes privados; refugios saturados
• Reportes artesanales (ej. "Plan Padrino") no escalan

5. HISTORIAS DE USUARIO
================================================================================

HU-01 — Registro de fundación
Como fundación, quiero registrarme, para publicar mascotas.
CA: nombre, email, contraseña, ciudad, organización | email único | HTTP 201

HU-02 — Registro de adoptante
Como adoptante, quiero registrarme, para enviar solicitudes.
CA: nombre, email, contraseña, ciudad | tipo Adoptante | HTTP 201

HU-03 — Inicio de sesión
Como usuario, quiero iniciar sesión, para acceder según mi rol.
CA: JWT con userId, email, rol | HTTP 401 si inválido

HU-04 — Publicar mascota
Como fundación, quiero publicar ficha, para que adoptantes la encuentren.
CA: nombre, especie, edad, tamaño, ciudad, descripción | estado Disponible

HU-05 — Buscar mascotas con filtros
Como visitante/adoptante, quiero filtrar, para encontrar la ideal.
CA: filtros combinables, paginación, endpoint público

HU-06 — Actualizar/eliminar mascota
Como fundación, quiero editar/eliminar mis fichas.
CA: solo propietario | no eliminar con solicitudes activas

HU-07 — Ver detalle de mascota
Como adoptante, quiero ver info completa, para decidir adopción.
CA: incluye datos fundación | HTTP 404 si no existe

HU-08 — Enviar solicitud de adopción
Como adoptante, quiero solicitar adopción, para iniciar proceso.
CA: estado Pendiente | mascota Disponible → EnProceso | HTTP 201

HU-09 — Gestionar solicitudes
Como fundación, quiero cambiar estados, para gestionar adopciones.
CA: Pendiente→EnRevision→Aprobada|Rechazada→Completada
    Al aprobar: mascota Adoptada, rechazar otras solicitudes

HU-10 — Consultar mis solicitudes
Como adoptante, quiero ver mis solicitudes, para seguimiento.
CA: solo del adoptante autenticado | orden por fecha

HU-11 — Reporte de impacto
Como fundación, quiero ver reporte, para medir impacto.
CA: disponibles, en proceso, adoptadas | filtro por fechas

HU-12 — Swagger UI | HU-13 — Mockups Figma
CA: /swagger con JWT | flujo completo responsive en Figma

7. MODELO DE DATOS
================================================================================

ENTIDAD            | CAMPOS CLAVE                          | RELACIONES
-------------------|---------------------------------------|------------------
USUARIO            | Id, Email(UK), PasswordHash, Tipo     | 1:0..1 FUNDACION
FUNDACION          | Id, UsuarioId(FK), NombreOrganizacion | 1:N MASCOTA
MASCOTA            | Id, FundacionId, Especie, Estado      | 1:N SOLICITUD
SOLICITUD_ADOPCION | Id, MascotaId, AdoptanteId, Estado     | N:1 MASCOTA, USUARIO

ENUMERACIONES:
TipoUsuario     { Fundacion, Adoptante }
TamanoMascota   { Pequeno, Mediano, Grande }
EstadoMascota   { Disponible, EnProceso, Adoptada }
EstadoSolicitud { Pendiente, EnRevision, Aprobada, Rechazada, Completada }

REGLAS DE NEGOCIO:
RN-01: Usuario Fundacion → exactamente 1 FUNDACION
RN-02: Solo una solicitud Aprobada/Completada por mascota
RN-03: Al aprobar → demás activas → Rechazada
RN-04: Mascota Adoptada no acepta nuevas solicitudes
RN-05: Email único en el sistema
RN-06: Índice MASCOTA(Especie, Ciudad, Estado)

12. DIAGRAMA DE SECUENCIA
================================================================================

FLUJO A — Adoptante envía solicitud:
Adoptante → MVC+JS → API Controller → SolicitudService → Repository → SQL Server
  1. Completa formulario
  2. POST /api/solicitudes { mascotaId, mensaje } + JWT
  3. Validar token y rol Adoptante
  4. Verificar mascota Disponible
  5. Verificar no hay solicitud activa duplicada
  6. INSERT Solicitud (Pendiente) + UPDATE Mascota (EnProceso)
  7. Retorna 201 Created

FLUJO B — Fundación aprueba:
  1. PUT /api/solicitudes/{id}/estado { Aprobada }
  2. Validar transición EnRevision → Aprobada
  3. UPDATE solicitud → Aprobada
  4. Rechazar otras solicitudes activas de la mascota
  5. UPDATE mascota → Adoptada (transacción atómica)
  6. Retorna 200 OK

    API->>Svc: CreateAsync()
    Svc->>DB: INSERT + UPDATE mascota
    DB-->>Svc: OK
    Svc-->>API: SolicitudDto
